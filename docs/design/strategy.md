# Corner Todo 디자인 전략 (v0.3 초안)

상태: 초안 · 작성 2026-11-24 · 갱신 2026-11-24 (단일 상황 → 상황의 범위와 적응 모델)

이 문서는 화면을 그리기 전에 정할 것들을 정한다. 무엇을 위해 디자인하는지, 무엇을 좋은 디자인으로 볼지, 어떻게 판단할지. 팔레트·글꼴 같은 시각 스타일은 이 문서가 확정된 뒤에 고른다.

---

## 1. 지금 디자인은 어떻게 나왔나

v0.1–v0.2 화면은 디자인 과정 없이 만들어졌다. 원인을 그대로 적는다.

| 원인 | 결과 |
|---|---|
| **목표가 "동작"이었다.** 기능 요구사항을 구현하면서 CSS를 그때그때 작성했다. 사용자·사용 상황·원칙 정의가 없었다 | 판단 기준이 없으니 모든 시각 결정이 기본값으로 떨어졌다 |
| **기본값의 평균.** 시스템 글꼴, 회색 바탕, 이유 없이 고른 초록, 둥근 카드, 테두리 알약 배지. AI가 만든 UI가 비슷해 보이는 이유는 학습 데이터의 가장 흔한 패턴으로 수렴하기 때문이고, 결정을 하지 않으면 기본값이 나온다 [10][11] | 어떤 할 일 앱에 붙여도 맞는 화면. 이 제품만의 것이 없다 |
| **검증이 기능 테스트뿐이었다.** 스모크 테스트는 "버튼이 눌리는가"만 봤고, "한눈에 읽히는가"는 아무도 재지 않았다 | 정보 과다, 작은 글자, 약한 위계가 그대로 통과했다 |
| **오버레이를 작은 메인 창으로 취급했다.** 주변 시야로 흘끗 보는 화면이라는 성격을 고려하지 않았다 | 오버레이에 목록·막대·배지·설명이 다 들어가서 1초 안에 읽히지 않는다 |
| **강조색 남발.** 버튼, 체크, 진행 막대, 토글, 탭, 현재 행, 상태 표시가 전부 같은 초록 | 중요한 것이 눈에 띄지 않는다. 신호 대 잡음비가 낮다 [4] |
| **이번 A/B/C 시안도 같은 실수.** 전략 없이 스타일(팔레트·글꼴)부터 골랐다. 사용한 도구는 "흔한 AI 티 제거" 점검표였지 디자인 전략 도구가 아니었다 | 겉모양 비교가 됐고, 무엇이 왜 좋은지는 답하지 못했다 |

## 2. 좋은 디자인이란

여러 출처가 겹치는 지점을 하나의 정의로 묶으면:

> **좋은 디자인은 특정 사용자가 특정 상황에서 목적을 가장 적은 주의와 마찰로 이루게 하고, 그 방식이 일관되어 믿을 수 있으며, 이 제품만의 성격이 드러나는 것이다.**

각 부분의 근거:

- **유용하고 이해하기 쉽다.** 제품은 쓸모가 있어야 하고 작동 방식이 스스로 드러나야 한다. 디자인은 눈에 띄지 않고 정직하며 마지막 디테일까지 일관된다. "가능한 한 적은 디자인" — 디터 람스 10원칙 [3]
- **신호 대 잡음비.** 미니멀은 유행 스타일이 아니다. 과업에 필요한 요소는 모두 있고 불필요한 요소는 없는 상태다. 평평한 디자인이라고 자동으로 미니멀이 되지 않는다 — NN/g 휴리스틱 8 [4]
- **최소한의 주의.** 기술은 가능한 한 적은 주의를 요구하고, 주변 시야를 활용하며, 문제를 푸는 데 필요한 최소한이어야 한다 — 캄 테크놀로지 [2]
- **흘끗 보고 이해된다.** 주변 디스플레이 연구의 네 원칙: 사용자 기대와 일치하는 표현, 핵심만 남긴 추상화, 서로·배경과 확실히 구별되는 시각 요소, 같은 정보는 같은 모양 [1]. 미묘한 차이(투명도, 크기 조금, 색 농도)는 한눈에 구별되지 않는다는 결과가 있다 [1]
- **위계와 일관성.** 형태와 기능이 분명한 위계를 세우고, 한 번 정한 모양과 동작은 끝까지 지킨다. 원칙은 "어떻게"가 아니라 "왜"를 알려준다 — Apple HIG [5]
- **작업이 초점, 나머지는 물러난다.** 모든 요소가 같은 무게를 가질 필요는 없다. 과업 중심 내용은 초점에, 탐색·지원 요소는 뒤로 — Linear [6]. 특정한 누군가를 위해 디자인해야 좋은 제품이 된다 [6]
- **단순함을 지키는 규율.** 생산성 도구는 단순해야 하며, 기능 요청은 앱을 복잡하게 만들지 않는지 신중히 따진다 — Things (Cultured Code) [7]
- **HUD의 규칙.** 자리를 얻을 자격이 있는 요소만, 가끔 필요한 정보는 상황에 따라 표시, 화면 가장자리에 배치, 크기·대비·위치로 중요도 구분, 같은 결정에 쓰는 정보는 묶기 [8]

## 3. 좋은 디자인은 어떻게 나오나

1. **문제를 먼저 정한다 (더블 다이아몬드).** 발견 → 정의 → 발전 → 전달. 앞의 다이아몬드는 문제 공간, 뒤는 해법 공간이다 [9]. 지금까지는 "정의"를 건너뛰고 "발전"(화면 그리기)으로 뛰었다.
2. **제품 전용 디자인 원칙을 쓴다.** 원칙은 사용자에게 줄 가치를 문장으로 쓴 것이고 디자인 결정의 기준이 된다. 일반 휴리스틱과 달리 제품마다 다르다 [12]. 명령형 한 문장 + 적용 예 + 무엇을 배제하는지 [12]. "직관적인 디자인" 같은 막연한 말은 원칙이 아니다 [12].
3. **레이아웃이 아니라 기능 하나부터.** 앱 전체를 한 번에 디자인하려 하면 막힌다. 실제 내용으로 핵심 화면 하나부터 만든다. 위계가 전부다 [13].
4. **기본값을 의식적으로 덮는다.** AI 도구는 결정이 아니라 기본값을 낸다. 맥락과 방향, 예시 화면을 주고 기본값(색·모서리·글꼴)을 하나씩 결정으로 바꾼다 [10][11].
5. **측정 가능한 평가 기준으로 검증한다.** 아래 8절.

6. **상황 하나가 아니라 상황의 범위를 설계한다.** 사용성은 "정해진 사용자가, 정해진 목표를, 정해진 사용 맥락에서" 이루는 정도로 정의된다 [14]. 같은 사람도 장소·작업·시간에 따라 맥락이 바뀐다. 제약은 영구적·일시적·상황적인 스펙트럼으로 나타나고, 가장 빡빡한 경우를 풀면 넓게 확장된다 [15].

## 4. 사용 맥락: 하나가 아니라 범위

Corner Todo는 한 사람의 한 장면을 위한 앱이 아니다. 같은 사용자도 하루에 여러 번 맥락이 바뀌고, GitHub로 배포되므로 다른 환경의 사용자도 있다. 그래서 맥락을 변수로 나누고 각 변수의 범위를 정의한다.

### 4.1 맥락 변수

| 변수 | 범위 | 디자인에 주는 의미 |
|---|---|---|
| 화면 | 노트북 한 대(13–14인치, 배율 125–150%) · 큰 모니터 한 대 · 다중 모니터(가로+세로) · 외부 모니터를 꽂았다 뺐다 | 크기는 화면 대비 상대값으로. 위치는 모니터 구성별로 기억하고, 모니터가 사라지면 남은 화면으로 옮긴다 |
| 오버레이 뒤 배경 | 어두운 코드 편집기 · 밝은 문서·웹 · 움직이는 영상·게임 | 배경에 기대지 않는 자체 판(plate)으로 대비 확보. 투명도에 하한 |
| 하는 일 | 깊은 집중(코딩·글쓰기) · 수동 시청(강의·영상) · 회의·화면 공유·발표 · 게임·휴식 | 같은 오버레이가 상황마다 다른 밀도와 표시 규칙을 가져야 함 |
| 손의 위치 | 키보드 위 · 마우스 위 · 손을 뗌(시청, 필기) | 주요 조작은 모두 단축키로도 가능. 클릭 대상은 충분히 크게 |
| 하루 중 시점 | 아침 계획 · 일하는 중 · 저녁 회고 | 메인 창은 계획과 회고 두 용도가 분명해야 함. 오버레이는 "일하는 중" 전용 |
| 시야 조건 | 밝은 낮 · 어두운 밤 · 피로 · 저시력 | 글자 크기·대비·테마를 사용자가 조절. 기본값부터 충분히 크게 |
| OS | Windows · macOS | 포커스·항상 위·전체화면 동작이 다름. 플랫폼별 구현, 같은 원칙 |

변수의 극단을 조합한 장면들. 시안과 구현은 이 장면 전부에서 원칙을 지켜야 한다.

## 5. 디자인 원칙 (초안)

결정이 갈릴 때 쓰는 기준이다. 원칙끼리 부딪히면 위의 것이 이긴다. 원칙은 모든 시나리오에서 같고, 바뀌는 것은 6절의 동작뿐이다.

### ① 방해하지 않는다
오버레이는 사용자의 주 작업보다 절대 크지 않다. 포커스를 가져가지 않고, 움직임과 소리는 상태가 바뀔 때만 쓴다.
- 적용: 클릭 후 원래 앱으로 포커스 반환(v0.2에서 측정·검증), 초과 시작·일정 도래 때만 한 번 신호, 게임·전체 화면 영상 위에서는 비켜남 (S3, S5)
- 배제: 상시 애니메이션, 반복 깜빡임, 매 동작마다 알림

### ② 한눈에, 하나만
오버레이는 1초 안에 세 가지만 답한다: 지금 할 일, 남은(초과) 시간, 진행량. 나머지는 접히거나 필요한 때만 나타난다.
- 적용: 다음 할 일 목록은 기본으로 접음, 일정은 도래했을 때만
- 배제: 오버레이 안의 설명문, 여러 개의 배지, 전체 목록

### ③ 상황에 맞춰 바뀌되, 예측할 수 있게
맥락에 따라 밀도와 표시가 바뀐다. 다만 바뀌는 규칙이 단순하고 눈에 보이며, 사용자가 되돌리거나 끌 수 있다 [20].
- 적용: 위치는 사용자가 둔 곳에 고정(습관), 자동 숨김은 이유를 표시하고 설정에서 끔
- 배제: 사용자가 모르는 사이 위치·크기가 바뀜, 끌 수 없는 자동 동작

### ④ 숫자가 주인공
이 앱이 다루는 실체는 시간과 양이다. 시간·진행량 숫자를 가장 크고 정확하게, 고정폭 숫자로 흔들림 없이 보여준다.
- 적용: 타이머가 오버레이에서 가장 큰 요소, 진행량은 "9 / 20쪽"처럼 단위와 함께
- 배제: 숫자 대신 장식 그래픽, 같은 정보를 막대·숫자·퍼센트로 세 번 표시

### ⑤ 색은 의미
색 하나에 의미 하나. 강조색은 "지금 진행 중"에만 쓴다. 초과와 일정 도래는 서로, 그리고 강조색과 확실히 구별된다 [1]. 색이 없어도 형태로 구별된다.
- 적용: 대기는 무채색, 집중 중만 강조색, 초과는 별도 의미색 + "+" 부호
- 배제: 버튼·토글·탭마다 강조색, 미묘한 농도 차이로 상태 구분

### ⑥ 기록은 정직하게, 탓하지 않게
계획 대비 실제와 초과 시간을 숨기지 않되, 실패로 그리지 않는다.
- 적용: "계획 50분 · 실제 62분 (+12분)"처럼 사실만
- 배제: 빨간 경고, 점수·등급, 연속 기록 끊김 같은 압박 장치

## 6. 적응 모델: 무엇이 고정되고 무엇이 바뀌나

**고정 (모든 맥락에서 같음)**
- 위치: 사용자가 둔 곳. 모니터 구성별로 기억 [17]
- 정보 위계, 색의 의미, 상태 표현, 단축키

**맥락에 따라 바뀜**

| 축 | 단계 | 언제 |
|---|---|---|
| 밀도 | **최소** — 한 줄: 할 일 + 남은 시간 | 대기 중, 작은 화면, 수동 시청 |
| | **기본** — 타이머 크게 + 할 일 + 진행량 | 집중 중 |
| | **펼침** — 서브 할 일, 다음 할 일, Work Time | 사용자가 펼칠 때 |
| 조작 | **고정** — 사용자가 정한 투명도, 조작 버튼 숨김, 클릭 통과 선택 | 평소 [16] |
| | **조작** — 불투명, 버튼 표시 | 마우스를 올리거나 단축키 |
| 표시 | **보임** | 기본 |
| | **비켜남** — 숨기거나 최소로 | 게임·전체 화면 영상·발표 감지 (S3, S5) |
| | **공유 화면에서 제외** — 내 화면엔 보이고 녹화·공유엔 안 잡힘 | 선택 (S4) |
| | **일시 확장** — 일정 도래 띠 | 일정 시각, 한 번 |
| 크기 | 화면 해상도·배율 대비 상대값 + 사용자 글자 크기 | 항상 |
| 테마 | 오버레이는 배경과 무관하게 대비가 확보되는 판 (어두운 판 기본, 밝은 판 선택) · 메인 창은 시스템 테마 | 항상 |

**자동으로 바뀌는 동작의 규칙** [20]
1. 왜 바뀌었는지 보인다 (예: 비켜났을 때 트레이 아이콘에 표시)
2. 한 번의 조작으로 되돌린다
3. 설정에서 끌 수 있다

## 7. 위계와 상태

**오버레이 정보 위계**

| 순위 | 요소 | 표현 | 밀도 단계 |
|---|---|---|---|
| 1 | 남은 시간 / 초과 시간 | 가장 큼, 고정폭 | 최소부터 |
| 1 | 지금 할 일 이름 | 두 번째로 큼 | 최소부터 |
| 2 | 진행량 (9 / 20쪽) | 중간 | 기본부터 |
| 3 | 서브 할 일, 다음 할 일, Work Time | 작고 흐리게 | 펼침 |
| 상황 | 일정 도래 | 1순위보다 위, 도래한 순간에만 | 모든 단계 |

**상태는 형태로도 구별한다** (회색조에서도 읽혀야 함)

| 상태 | 신호 |
|---|---|
| 대기 | 무채색, 시작 표시 |
| 집중 중 | 강조색, 시간 줄어듦 |
| 일시정지 | 흐려짐 + 일시정지 표시 |
| 초과 | 별도 의미색 + "+" 부호, 시간 늘어남 |
| 일정 도래 | 맨 위 띠, 한 번만 신호 |

## 8. 평가 기준

"예뻐 보인다"는 기준이 아니다. 시안과 구현은 아래를 통과해야 한다.

1. **시나리오 점검:** S1–S6 각각에서 원칙 ①–⑥이 지켜지는지 직접 재현해 본다
2. **환경 매트릭스:** 1366×768·125% / 1920×1080·100% / 3840×2160·150%, 어두운·밝은·움직이는 배경에서 캡처해 비교
3. **1초 글랜스 테스트:** 오버레이 캡처를 1초 보고 "지금 할 일, 남은 시간, 진행량"을 말할 수 있는가 [1]
4. **회색조 테스트:** 색을 빼도 위계와 상태가 읽히는가
5. **방해 측정:** 오버레이 조작 전후 활성 창 유지 (v0.2 측정 방법 재사용)
6. **원칙 대조:** 화면의 모든 요소가 원칙 하나로 설명되는가. 설명 안 되면 뺀다
7. **일관성:** 같은 정보는 메인·오버레이에서 같은 모양
8. **접근성:** 텍스트 대비 4.5:1 이상, 키보드 포커스 표시, 글자 200%에서도 깨지지 않음
9. **템플릿 테스트:** 제품 이름을 다른 앱으로 바꿔도 화면이 어울리면 실패

## 9. 실제 사용으로 확인할 가정

아래는 분석으로 정한 판단이고, 실제 사용 기록(JSONL 로그)으로 맞는지 확인한다.

| 가정 | 확인 방법 |
|---|---|
| 대기 중에는 최소 밀도(한 줄)로 충분하다 | 펼침 조작 빈도, 대기 중 메인 창을 여는 빈도 |
| 자동 비켜남이 기대와 맞는다 | 비켜난 직후 수동으로 다시 띄우는 비율 |
| v0.1에서 할 일을 안 넣은 이유는 입력 부담이다 | 빠른 입력 사용 빈도, 할 일 생성 경로별 비율 |
| 위치를 한 번 정하면 거의 안 옮긴다 | 위치 변경 이벤트 빈도 |

로그에 아직 없는 이벤트(펼침, 비켜남, 위치 변경 등)는 구현 때 추가한다.
